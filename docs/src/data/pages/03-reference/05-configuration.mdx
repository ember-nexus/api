Ember Nexus API can be configured through environment variables (database connections, common options) and by providing
a YML config file for lesser used settings.

A refactoring of the configuration process is planned in [issue #463](https://github.com/ember-nexus/api/issues/463).

## Environment variables

Ember Nexus specific variables:

- `ANONYMOUS_USER_UUID`: The UUID of a user, which will be used if no token is supplied.
- `ANONYMOUS_USER_READONLY`: Set to `false` to allow the anonymous user to also use write endpoints (`POST`,
`PUT`, `PATCH`, `DELETE`, ...). Defaults to `true`, i.e. anonymous requests are restricted to read-only (`GET`,
`HEAD`) endpoints, plus a handful of endpoints that do not require authentication by design, such as
[`POST /token`](/api/post-token), [`POST /register`](/api/post-register) and [`POST /search`](/api/post-search).
- `CYPHER_AUTH`: Connection string for accessing the OpenCypher database, i.e. Neo4j.
- `MONGO_AUTH`: Connection string for accessing the Mongo database.
- `ELASTIC_AUTH`: Connection string for accessing the Elasticsearch database.
- `S3_ENDPOINT`: URL of the S3-compatible storage API, e.g. `http://minio:9000`.
- `S3_ACCESS_KEY_ID`: Access key ID used to authenticate against the S3-compatible storage API.
- `S3_SECRET_ACCESS_KEY`: Secret access key used to authenticate against the S3-compatible storage API.
- `REDIS_AUTH`: Connection string for accessing the Redis database.
- `RABBITMQ_AUTH`: Connection string for accessing the RabbitMQ database.
- `VERSION`: Variable containing the version of the currently running API software. Automatically set by the build
process.
- `REFERENCE_DATASET_VERSION`: Variable containing the version of the
[reference dataset](https://github.com/ember-nexus/reference-dataset) used for validating features.
- `DISABLE_CRON`: Set to `true` to disable the [background tasks](#background-tasks) every API instance would
otherwise run automatically. Defaults to `false`.

Framework specific variables:

See [Symfony's documentation](https://symfony.com/doc/current/configuration.html#configuration-based-on-environment-variables)
for details.

## Background tasks

Every API container instance schedules
[`cron:update-ownership`](/command/cron-update-ownership),
[`cron:reindex-files`](/command/cron-reindex-files) and
[`cron:delete-expired-uploads`](/command/cron-delete-expired-uploads) internally, each on its own interval, for as
long as the container is up - there is nothing to schedule externally, and running multiple instances in parallel is
safe since the individual tasks consume their work from a shared RabbitMQ queue, so the same item is never processed
twice regardless of how many instances happen to poll at once. Set the `DISABLE_CRON` environment variable to `true`
on an instance to opt it out, e.g. to run these commands on a different schedule yourself instead.

## File storage buckets

Ember Nexus stores uploaded files in two separate S3-compatible buckets: `file.S3UploadBucket` holds chunks of
resumable uploads still in progress, and `file.S3StorageBucket` holds files that have been fully attached to an
element - see [Chunk storage](/reference/upload#chunk-storage) for how a file moves from one
to the other. Ember Nexus already cleans up expired uploads itself (see [Expiry](/reference/upload#expiry) and the
[background tasks](#background-tasks) above), but only while those tasks are actually running. As a backstop,
operators should also configure an object lifecycle policy directly on the upload bucket: expire objects after
roughly 24-48 hours, and abort incomplete multipart uploads after a similarly short period. Ember Nexus neither
creates nor manages this policy - it must be set up on the bucket itself, outside of this repository:

- [AWS S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html): covers both object
  expiration and `AbortIncompleteMultipartUpload`.
- [SeaweedFS](https://github.com/seaweedfs/seaweedfs/wiki/S3-Lifecycle): supports lifecycle expiration rules.
- [VersityGW](https://github.com/versity/versitygw/wiki/S3-API-reference#recognized-but-not-implemented): lifecycle
  configuration is recognized but not implemented - keep the background tasks running instead.

The storage bucket holds permanently retained files and should not have such a policy applied to it.

Ember Nexus does not create these buckets itself - they must already exist on the S3-compatible storage before the
API starts, named exactly as configured (`api-storage` / `api-upload` by default). The
[Docker Compose example](/getting-started/installation#docker-compose) includes a `minio-init` container that creates
both buckets on a fresh MinIO instance; without it (or an equivalent manual `mc mb` / console step) the
[`healthcheck`](/command/healthcheck) command fails and uploads and downloads do not work.
