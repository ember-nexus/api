# UuidToTypeMphfLookup

Resolves an element id to its type (node label or relationship type) in about 100-400 ns, in process, from a
compact static structure instead of a database scan.

* `mphf/` - the pure Go library: `.mphf` file format, builder (BBHash, SipHash-2-4-128 with a per-build key,
  fallback table), and the memory mapped reader.
* `cmd/mphf-builder` - CLI: `build` (CSV to `.mphf`), `verify`, `lookup`.
* `cmd/mphf-gen`, `cmd/mphf-bench` - test data generator and lookup benchmark.
* `extension/` - the FrankenPHP extension (own Go module), PHP namespace `EmberNexus\Mphf`.

The PHP side (build command, version sync, Redis overlay, type service) lives in the API's `src/`.

## Properties

* ~`3.7 + w` bits per key (`w` = ceil(log2(types)) bits for the packed type index), i.e. ~110 MB for 100M elements
  and 30 types.
* **No membership information.** An id that was not part of the build usually returns *some* type. Callers must use
  the result only as a candidate, e.g. in a typed query that then finds nothing.
* Keys are the canonical 37 character base62sort ids. All keys go through SipHash-2-4 (128 bit) with a random key per
  build, so ids chosen by clients can not be crafted to collide or make a build fail. Keys that still collide after
  `MaxLevels` BBHash levels end up in a sorted fallback table, so a build never fails because of the data.
* The file is used directly from `mmap`, there is no deserialisation. Opening a file checks the length, the SHA-256 of
  the content (one sequential read, optional via `OpenOptions.SkipHashCheck`) and the structure; `mphf-builder verify`
  additionally checks rank checkpoints, value range and the fallback table. The PHP downloader checks length and hash
  before a download is published.
* **Collisions.** Keys are identified by their 128 bit hash. Position collisions inside the BBHash levels are resolved
  by further levels and finally the fallback table, so every key of a build gets its own slot. Two different ids with
  the same 128 bit hash (about 1e-23 at 100M keys) are merged if they have the same type, and fail the build with a
  `ConflictError` if their types differ; a wrong type is never written silently. `mphf-builder build` solves this itself:
  every build uses a new random hash key, so on such a hash collision it simply builds again (up to 5 times). The same
  id with two types in the input is a data error instead; it is not retried and the conflicting lines are printed.

## Input format

UTF-8, no header, `\n` line endings, `;` separator, one element per line: `<id>;<type>`. The builder rejects lines
without exactly one `;`, ids that are not 37 characters of `[0-9A-Za-z]`, empty or longer than 255 byte types, and
types containing control characters. The same id with the same type twice is accepted; with different types the
build fails and lists the conflicting lines.

## File format

A file starts with a human readable preface, so `head` or `cut` show where it comes from:

```
MPHF
generated by: Ember Nexus API 0.2.0
generated on: 2026-11-22 18:14
content length: 110000000
sha256: <64 lowercase hex characters, then spaces up to a multiple of 64 bytes>

<content>
```

The content starts after the first `\n\n` of the file (searched within the first 1024 bytes). `content length` and
`sha256` (SHA-256 of the content) are required, unknown lines are ignored. A reader rejects files whose content length
differs from the real one.

**Padding rules.** The content starts at an offset which is a multiple of 64, so its sections stay cache line aligned
inside the page aligned mapping. To get there, the writer appends spaces directly behind the hash. Writers and readers
(Go and PHP) enforce:

- the offset of the content is a multiple of 64;
- the only padding are spaces directly behind the 64 hash characters, and there are fewer than 64 of them;
- no other line ends with a space (`mphf-builder build --generator` rejects such a generator text).

The writer checks its own output against these rules before it writes a file; a violation is an internal error.

### Content (version 1)

Little endian, every section starts on a 64 byte boundary (relative to the start of the content), the section table has
to be canonical (a reader rejects files whose offsets differ from the layout derived from the section lengths).

| Section | Contents |
|---|---|
| Header (256 B) | magic `ENMPHF\0\x01`; `formatVersion u16 = 1`; `algorithm u16 = 1`; `flags u32`; `createdAtMs u64`; `watermarkMs u64`; `keyCount u64`; `hashKey [16]B`; `gammaMilli u32`; `levelCount u32`; `valueWidth u8`; `placedCount u64` (offset 72); `fallbackCount u64` (offset 80); section table `(offset u64, length u64)` x 6 at offset 96 |
| Type dictionary | `typeCount u32`, then per type `len u8` + name. The index is the position; names are sorted. |
| Level table | per level `bitOffset u64`, `bitLength u64` (multiples of 64 bits) |
| Bit vectors | all levels concatenated, `u64` words |
| Rank checkpoints | one cumulative `u64` popcount per 512 bits |
| Values | `w`-bit packed type indices in MPHF index order + 8 B padding |
| Fallback table | `count u64`, then records sorted by hash: `h0 u64`, `h1 u64`, `typeIndex u16` |

Lookup: `(h0, h1) = SipHash128(key)`; for each level `i`: `pos = mulhi(fmix64(h0 ^ rotl(h1, 29) ^ (i+1) * 0x9e3779b97f4a7c15), levelBits)`;
if that bit is set, `index = rank(levelOffset + pos)` and the type is `values[index]`. If no level hits, binary search
the fallback table by `(h0, h1)`.

## Protection of the mapped file

Built and downloaded files are read-only (`0444`), so nothing in the container writes into a mapped file. If a file is
truncated or its storage vanishes while it is mapped anyway, the kernel answers the next access with SIGBUS, which
kills a Go program. `Table.SafeLookup` (used by the PHP extension) and `Open` therefore run with
`debug.SetPanicOnFault(true)` and return `ErrMappingFault` instead. The extension then drops the table, so PHP answers
without it (a typed query instead of the table lookup), and the PHP side removes a local file which fails its checksum
and downloads it again. `Table.Lookup` is the unprotected, faster variant for callers who own the file.

## Working on the Go code

No Go installation is needed, use the pinned container (the extension itself needs PHP headers and is compiled by the
API's Docker build):

```shell
docker run --rm -v "$PWD:/src" -w /src golang:1.27.4-alpine sh -c 'apk add --no-cache gcc musl-dev && go vet ./... && CGO_ENABLED=1 go test -race ./...'
docker run --rm -v "$PWD:/src" -w /src golang:1.27.4-alpine go test -run xxx -fuzz FuzzParseTable -fuzztime 60s ./mphf/
```

Benchmarks:

```shell
mphf-gen --count 10000000 --types 30 > elements.csv
mphf-builder build --input elements.csv --output elements.mphf --generator 'Ember Nexus API dev'  # prints time, size and peak memory as JSON
mphf-bench --mphf elements.mphf --csv elements.csv --threads 8
```

Measured on a laptop class machine with 10M random sv2a7 shaped ids and 30 types: build 0.7 s plus 0.8 s CSV parsing,
10.9 MB file (8.7 bits/key), builder peak RSS 211 MB (about 21 bytes per key, so about 2.1 GB for 100M keys: the builder
keeps a 128 bit hash and a 16 bit type per key), lookups ~260 ns single threaded in Go with a warm cache.
